# TrFileTransfer v2 线协议（Rust 版字节级定义）

| 项 | 内容 |
|------|------|
| 文档性质 | **字节级协议权威**（产品级语义见 [PRODUCT-SPEC.md](PRODUCT-SPEC.md) §4；实现以 `trft-core::protocol` 与本文为准，二者由判别测试互锁） |
| 适用范围 | 本 Rust 实现自互通；**与原 C# 版不做互通承诺**（TECH-STACK §4） |
| 字节序 | 多字节整数一律**小端（LE）** |
| 字符串 | UTF-8；`u16 长度 + 字节` 前缀式（下记 `str16`）；路径段以 `/` 分隔 |
| 抽取基线 | M3'（2026-10-31）：0x00–0x06、0x08–0x0C、0x10/0x11/0x1A 全量落地 |

## 1. 传输与栈结构

```
应用帧（§3）
  ▲
Compressed（可选，0x08 协商后）        ← 压缩装饰器在帧层之下、加密之上
  ▲
Encrypted（可选，0x09）或 QUIC TLS     ← 机密性/认证
  ▲
TCP
```

- 装饰器包裹顺序固定为 `encrypt(compress(plain))`——压缩内层、加密外层（规格 §4.1）。
- QUIC 槽位：TLS 1.3 承担机密性，流上**先发 1 字节协议版本号 `0x02`** 再进帧层；
  TCP 槽位无版本前缀（未知帧 fail-closed 兜底）。
- 前导组合顺序：认证在前（`0x09` 首选 → `0x05` 明文门）、`0x0A` 能力协商、`0x08` 压缩协商次之，
  之后才允许业务帧。`0x0A`/`0x08` 各**至多一次**，顺序不限（本实现客户端固定先 `0x0A` 后 `0x08`）。

## 2. 前导协商

### 2.1 认证

| 方向 | 字节 |
|---|---|
| C→S | `0x09` + 65B 临时 ECDH P-256 公钥（或明文门 `0x05`） |
| S→C | `0x19` + 65B 公钥 |
| 通道内（加密后） | C→S `u8 flags + [32B HMAC 证明]`；S→C `u8 status + u8 flags + [32B HMAC 证明]` |
| 明文门 `0x05` | C 宣告 `0x05` → S 回 16B 盐 → C 回 32B 证明 = `HMAC(PBKDF2-HMAC-SHA256(码,盐,50k), 盐‖"trft-pair-v2")` → S 回 1B 结论（`0x01`/`0x00`） |
| 通道绑定门 `0x0D`（M6'，**仅 QUIC 槽位**，双向确认） | C 宣告 `0x0D` → S 回 `0x1D` + 16B 盐 → C 回 32B 证明 = `HMAC(K, "trft-pair-bind-v1"‖盐‖S_fp)`，其中 `K = PBKDF2(码,盐,50k)`、`S_fp = SHA-256(客户端实际所见服务器证书 DER)` → S 回 `0x01` + 32B S→C 证明 = `HMAC(K, "trft-pair-bind-s2c-v1"‖盐‖S_fp)`（客户端恒时校验——盲接受型假服务端必败，轮 2 P1）；拒绝时 S 回裸 `0x00` |

服务端有码而首帧非 `0x05`/`0x0D` → 不写盐直接回 `0x00` 并关闭（确定性拒绝）。

**通道绑定语义（M6'）**：QUIC 槽位配对启用时，新版服务端**强制** `0x0D`（收到明文
`0x05` 直接拒绝——旧版客户端须升级）；S 以自身证书指纹校验。双臂中继（MITM 两腿各自
终结 TLS）两腿证书必然不同 → 证明必败；透明字节级中继不构成 MITM（TLS 完整性保护）。
S→C 证明同时封死「假服务端盲接受」——MITM 不知配对码即无法伪造 s2c 证明（轮 2）。
新客户端遇旧服务端（对 `0x0D` 回 `0x00`/断连，无 `0x1D` 前导）自动回退明文 `0x05` 并记
警告——回退只可能发生在旧服务端上。明文 TCP `0x05` 无通道材料可绑定（无 TLS/DH），
双臂中继不可防——既有残余风险，靠 0x09 默认启用缓解。`0x1D` 盐前导兼作旧服务端判别
（旧版对未知 `0x0D` 回裸 `0x00`）。

### 2.2 能力协商 `0x0A` / `0x1A`

| 方向 | 字节 |
|---|---|
| C→S | `0x0A` |
| S→C | `0x1A` + `u8 caps` |

| bit | 能力 |
|---|---|
| 0 | 接受 `0x02` 分块文件 |
| 1 | 接受 `0x0B` 覆盖率查询（规格 §4.1 保留位） |
| 2 | 接受 `0x03` 单文件续传 |
| 3 | 接受 `0x04` 文件夹续传/同步 |
| 4 | 接受 `0x08` 压缩协商 |

客户端对旧对端**无需先探询**：直接发扩展帧，未知帧对端回 `0x00` 并断开（§3.8），
客户端据此走降级路径（fresh 连接重发 `0x00`/`0x01`）。

### 2.3 压缩协商 `0x08` / `0x18`

| 方向 | 字节 |
|---|---|
| C→S | `0x08` |
| S→C 接受 | `0x18`（此后双方把流包进压缩装饰器，协商字节本身**不经**压缩） |
| S→C 拒绝 | `0x00`（连接继续，明文直传——宽容降级） |

`0x08` 仅在认证完成后被接受（防预认证内存放大，规格 §4.1）。

## 3. 帧定义

所有帧以 1 字节类型开头。完成确认统一为 S→C `1B`：`0x01` 接受 / `0x00` 拒绝
（`0x00`/`0x01`/`0x06`/`0x04` 处理后必回；结果未知 ≠ 成功）。

### 3.1 `0x00` 单文件

| 字段 | 类型 |
|---|---|
| type | `u8 = 0x00` |
| name | `str16`（净化：拒路径分隔/ADS/保留名/尾点，见 `sanitize_name`） |
| size | `u64` |
| payload | `size` 字节 |
| sha256 | 32B（整文件） |

### 3.2 `0x01` 文件夹

| 字段 | 类型 |
|---|---|
| type | `u8 = 0x01` |
| rootName | `str16` |
| fileCount | `u32`（≤ 1,000,000） |
| 逐文件 | `str16 rel` + `u64 size` + `payload` + 32B sha256（rel 按 `/` 分段净化） |
| 完成确认 | S→C 1B（整夹判决，带内） |

### 3.3 `0x02` 分块文件（Rust v2 定义）

每块独立自描述；1–8 条连接并行写同一 groupId，块按**声明偏移**落盘（幂等）。

| 字段 | 类型 |
|---|---|
| type | `u8 = 0x02` |
| groupId | 16B（客户端每次全新生成；源文件变化必须换新 groupId 全量重发） |
| offset | `u64`（本块在整文件中的偏移） |
| totalSize | `u64`（会话内所有块必须一致，`> 0`，≤ 1 PiB） |
| name | `str16`（会话内所有块必须一致） |
| payloadLen | `u32`（≤ 8 MiB） |
| payload | `payloadLen` 字节 |

- **完成判据 = 覆盖**：服务端区间合并排序后覆盖 `[0, totalSize)`，不按字节累加；
  合并区间数 > 8,192 拒收（慢速 DoS 守卫）。
- 已覆盖区间的重复块**跳过写盘**（幂等 + 防组装与迟到处写竞态）。
- 覆盖达成后服务端**现算整文件 SHA-256** 登记摘要缓存并原子发布（hard_link fail-if-exists）。
- 服务端会话表上限 64 组；10 分钟无块逐出并删除半成品（`.trft-part` 受 7 天孤儿清扫兜底）。

### 3.4 `0x0B` 分块覆盖率查询

| 方向 | 字段 |
|---|---|
| C→S | `u8 = 0x0B` + 16B groupId |
| S→C 已知 | `u8 0x01` + `u32 n` + n × (`u64 offset`, `u64 len`)（合并区间，升序） |
| S→C 未知 | `u8 0x00`（服务端无状态/已组装/被逐出 → 客户端回退全量重发） |

暂停/继续（v2.14 语义）：继续时先查询，客户端对补集补发 `0x02`。

### 3.5 `0x0C` 分块收尾

| 方向 | 字段 |
|---|---|
| C→S | `u8 = 0x0C` + 16B groupId（本连接不再发块） |
| S→C | 1B：`0x01` = 该组已组装完成（本连接至少目睹组装完成）；`0x02` = 会话存在但尚未覆盖；`0x00` = 会话不存在 |

客户端判决：全部连接 `0x01` → 成功；任一 `0x00` → 整组失败；仅 `0x02` → 再查 `0x0B` 补发（≤3 轮）。
**未目睹 `0x01` 不得报成功**（防「补集算错仍假成功」）。

### 3.6 `0x03` 单文件续传

| 方向 | 字段 |
|---|---|
| C→S 请求 | `u8 = 0x03` + `str16 name` + `u64 size` + `u64 declaredOffset` + `u8 verifyFlag` + 32B 整文件 SHA-256 |
| S→C 协商 | `u8 = 0x10` + `u8 status` + `u64 serverOffset` |
| C→S 载荷 | `size - serverOffset` 字节 + 32B 整文件 SHA-256（重复携带，防源文件传输中变异） |
| S→C 确认 | 1B（`0x01`/`0x00`） |

`status`：`0x01` = 从 `serverOffset` 续传；`0x02` = 命中已有相同文件（去重 skip），**零传输**；
`0x00` = 拒绝（大小非法/偏移越界/校验失败等）。

规则（规格 §3.1）：
- `serverOffset` **服务端权威** = `max(declaredOffset, 服务端实际半成品长度)`；服务端无状态时从 0。
- `size == 0` 拒绝（空文件走 `0x00`——客户端回退）。
- 会话绑定 `对端 IP + 文件名`（per-session 锁防跨连接并发写坏）；半成品名确定性派生自二者，
  侧车 `.meta` 记录 `(size, claimed hash)`——meta 失配视为陈旧前缀，**删除半成品从 0 重来**
  （陈旧前缀保护：大小相符的旧版本完整文件绝不拼接）。
- 完整哈希**必须在建连之前算完**（客户端义务）；服务端收完对整文件重读比对，
  不一致 → 真删除半成品 + 回 `0x00`（Rust v2 对 verifyFlag=0/1 都执行重读比对，
  `verifyFlag` 字段保留线兼容语义）。
- `DuplicateFiles=skip` 且目标已有同内容文件 → `status=0x02` 零传输（哈希经缓存或现算比对）。
- 半成品 `.trft-resume` + `.meta`；7 天孤儿清扫（规格 §6.1）。

### 3.7 `0x04` 文件夹续传/同步

| 方向 | 字段 |
|---|---|
| C→S 清单 | `u8 = 0x04` + `u64 sessionId` + `str16 rootName` + `u32 fileCount`（≤ 100,000，Rust v2 上限）+ 逐项 `str16 rel` + `u64 size` + `u8 hasHash` + [32B hash] |
| S→C 协商 | `u8 = 0x11` + 位图（`ceil(fileCount/8)` 字节；bit i=1 → 第 i 项服务端已确认同内容，**跳过**） |
| C→S 载荷 | 逐个未跳过文件：`str16 rel` + `u64 size` + `payload` + 32B sha256 |
| S→C 确认 | 1B（整夹带内判决） |

- 清单在建连前构建；`hasHash=0` 的项服务端**必然回 0**（服务端无从证明同内容 → 判错方向是多传一次）。
  客户端哈希来自其摘要缓存命中（免费）；缓存未命中直接入「必发」集合。
- 服务端逐项核对：目标存在 + 大小相符 + 哈希一致（服务端缓存命中或 spawn_blocking 现算）。
- **同步语义**：根目录固定 `saveDir/rootName`（不追加 `_1`——跨次同步必须同一目录）；
  传递中内容不同的文件以「校验后 rename 覆盖」更新；**本地已删除的文件服务端保留**（增量备份）。
- `sessionId`：由 `(源路径, 目标地址)` 确定性派生（大小写/尾斜杠不敏感，见 `stable_session_id`），
  本实现中线不改变行为（差分无状态：磁盘文件即状态），保留字段供会话枚举/重置。
- 每文件哈希不一致 → 服务端删除半成品、中止整夹（客户端必然以错误收场，杜绝假成功）。

### 3.8 未知帧

S 对未知类型回 `0x00` 后关闭（排水 ≤500ms 防 RST 吞拒绝字节）。客户端把
「扩展帧收到 `0x00` 且无 `0x10`/`0x11` 前缀」判为**对端不支持**，走降级/显式报错。

## 4. 压缩装饰器（0x08 之后）

段格式（每 `poll_write` 输入一段，独立成帧）：

| 字段 | 类型 |
|---|---|
| rawLen | `u32`（解压后长度，≤ 64 MiB——解压炸弹守卫与精确性校验） |
| wireLen | `u32`（线上载荷字节数——mode=1 时压缩流长度 ≠ rawLen，读侧按此取段） |
| mode | `u8`：0 = 原样（零膨胀直传），1 = deflate |
| payload | `wireLen` 字节；mode0 必须 wireLen == rawLen，mode1 解压必须**恰好**产出 rawLen 字节（超出/不足即错） |

- 算法 deflate（flate2/miniz_oxide，`Compression::fast()`）；写前采样 ≤64KB，
  压后 ≤30% 才压整段，否则 mode=0（不可压缩数据零膨胀，规格 §6.2）。
- 段长 < 64B 一律 mode=0（最小压缩段，规格 §6.1）。
- 读侧限制：rawLen > 64 MiB 拒绝；解压输出以 rawLen 为硬上限。

## 5. 单向 UDP 帧（无回传，另行体系）

20B 公共头（`u8 version=2` + `u8 frame` + `u8 pad[6]` + `u64 session` + `u64 seq`，小端）：

| frame | 载荷 |
|---|---|
| `0x01` START | `u16 名长` + 名 + `u64 size` + `u32 块长` + `u8 fec` + `u8 parity`（连发 3 份，间隔 40ms） |
| `0x02` DATA | seq=全局块序号，载荷=该块（末组补零到块长） |
| `0x03` END | 32B SHA-256（连发 3 份） |
| `0x04` PARITY | `u32 组号` + `u8 分片序号(≥k)` + RS 分片 |

会话 ID = (文件名, 大小, mtime) 确定性派生——重发即续传，接收方「落盘即状态」。
PARITY 对旧接收端无需协商（静默忽略）。

## 6. 设备发现（UDP 广播，仅 IPv4，规格 §3.3）

无握手、无回传通道外的独立小协议；多字节整数小端。默认端口 45000（`discovery_port`）。

### 6.1 请求帧 0xD1

| 字段 | 长度 | 说明 |
|---|---|---|
| frame | 1 B | `0xD1` |
| name_len | 2 B | 请求方本机名字节数 |
| name | name_len | UTF-8 本机名（供对端记录；≤ 64 B） |

### 6.2 应答帧 0xD2

| 字段 | 长度 | 说明 |
|---|---|---|
| frame | 1 B | `0xD2` |
| name_len | 2 B | 应答方本机名字节数 |
| name | name_len | UTF-8（≤ 64 B） |
| flags | 1 B | bit0 = TCP 监听中；bit1 = UDT 监听中；bit2 = 需配对码 |
| tcp_port | 2 B | TCP 监听端口（flags bit0=0 时为 0） |
| udt_port | 2 B | UDT(QUIC) 监听端口（flags bit1=0 时为 0） |

- 守卫：整包 > 512 B、name > 64 B、截断/坏帧 → **整包忽略**（fail-closed）。
- 应答方仅在有 TCP/UDT 监听器时运行，flags 实时读取；请求方按应答源 IP 去重。
- 语义锚点：`trft-core::discovery`（编码/解码/发现/应答由单元与回环 e2e 互锁）。
