# 真机验证清单（v2 / 2026-11-16）

本清单覆盖三类只能在真机上定论的验证：**C# 2.14 互通回归**、**NTFS 掉电 fsync**、
**GUI 冒烟**。每条含步骤、预期与「关联改动」，用于每轮协议/落盘改动后的回归，
也用于发版前验收。

> 自动化测试（`cargo test --workspace`，当前 296 项）覆盖协议逻辑与错误路径；
> 本清单覆盖自动化测不到的部分：**与外部实现的线级互通**、**掉电语义**、**人机流程**。

## 0. 前置条件

| 项 | 要求 |
|---|---|
| 构建 | `cargo build --release --workspace`（产物在 `target\release\`） |
| 机器 | 两台 Windows 10/11 x64，同一 LAN，保存目录为 **NTFS** 本地盘 |
| 对端 | C# 版 **TrFileTransfer 2.14.0.0**（互通仅走 UDT 槽位，TECH-STACK §7.30） |
| 端口 | 默认 8080（TCP/QUIC/RUDP/UDT 各自独立；HTTP 共享 8090）；首次启动放行防火墙 |
| 取证 | 两端日志 + `Get-FileHash -Algorithm SHA256` 输出 +（掉电项）VM 快照 |
| 目录 | 每次用例用全新空目录；失败后保留现场再复跑 |

常用命令（Rust 侧）：

```bat
trft recv --proto udt --port 8080 --out D:\recv
trft send --proto udt --ip 192.168.1.20 --port 8080 --file D:\src\big.zip
trft sync --proto udt --folder D:\work --ip 192.168.1.20 --port 8080
trft verify --dir D:\recv
```

哈希：`Get-FileHash -Algorithm SHA256 <文件>`（或 `certutil -hashfile <文件> SHA256`）。

## A. C# 2.14 互通回归

**统一口径**：两侧协议都选 **UDT**；除特别说明外，端口 8080、明文、关闭压缩。
每项都要**双向**各做一次（Rust→C#、C#→Rust），并把两端 `SHA-256` 抄进记录表。

### A1 单文件（0x00）
1. C# 接收，Rust `trft send --proto udt --file`；再反向。
2. 预期：对端显示完成；接收文件长度与 SHA-256 与源一致；无 `.trft-part` 残留。
3. 关联改动：无（基线回归）。

### A2 大文件（> 4 GiB）
1. 生成 5 GiB 随机文件；双向各传一次。
2. 预期：SHA-256 一致；C# 侧进度不因 32 位边界回绕/负值；Rust 侧不因 `u32` 截断失败。
3. 关联改动：0x00 长度字段（基线）。

### A3 文件夹（0x01）
1. 目录含 3 层子目录、1 个空目录、1 个 0 字节文件；双向。
2. 预期：层级与空目录保留；0 字节文件存在且哈希一致；重复发送不重复建目录。

### A4 文件名边界（本轮改动）
1. 准备 `a..b.txt`、`v1..2.log`、`报告 2026-11-16.txt`、`x y  z.txt`、200 字符长名。
2. 预期：前三者**能发能收**（`..` 作为子串不再被拒）；`../x`、`a\..\b` 仍被拒（应报错而非落盘）；
   超长名按平台上限报错，不得截断成同名冲突。
3. 关联改动：`sanitize_name` 去掉 `..` 子串一票否决。

### A5 分块（0x02）正常完成
1. Rust `trft send --proto udt --chunks 4 --file big.zip`；C# 侧接收。
2. 预期：0x0B 覆盖进度推进；0x0C 得 0x01（成功）；最终 SHA-256 一致；对端只收到一个最终文件。
3. 关联改动：0x02 组装前 fsync；会话按来源分桶（单 peer 8 组）。

### A6 分块（0x02）中断与重传
1. 传输中途禁用网卡 5 秒后恢复（或结束 C# 接收进程再重启）。
2. 预期：失败侧收到**显式错误**（不是「完成」）；重传后 SHA-256 一致；
   若中途组装器被回收，发送端必须收到「请整组重发」类错误而非假成功。
3. 关联改动：0x02 tracker 缺失显式报错（本轮 P0 批）。

### A7 续传（0x03）与参数变化（本轮改动）
1. 传 1 GiB 文件，进度 50% 时杀发送进程；重启同一命令。
2. 预期：续传从磁盘实际长度继续（偏移=磁盘事实）；最终 SHA-256 一致。
3. **同一 sessionId 改参数**：中断后把源文件改成不同大小/名字再用同 sid 发。
   预期：不得删除**已验证交付**的旧文件；未验证半成品可清理；结果不得报成功。
4. 关联改动：0x03 会话选择重写、`verified`/`declared_held`、长度硬校验。

### A8 续传（0x03）残件截断
1. 中断后手工把接收端 `.part` 文件截短 1 KiB，再续传。
2. 预期：服务端回「续传残件长度不符，需整组重发」类错误；不得回 status 2（完成）；
   客户端整组重发后 SHA-256 一致。
3. 关联改动：0x03 长度硬校验 + 尾哈希必需。

### A9 目录同步（0x04）成功与失败保留
1. 首次 `trft sync` 同步 20 个文件；修改 5 个、删除 3 个、新增 2 个，再同步。
2. 预期：差异正确落地；删除按协议语义处理；SHA-256 全一致。
3. **失败路径**：同步中途对端断线/拒绝。预期：**已存在的旧文件必须原样保留**，
   不得被截断或删除；重试后成功。
4. 关联改动：0x04 原子替换（`cs_publish_replace`）、失败分支不再动 `save_path`。

### A10 目录同步（0x04）会话目录复用（本轮改动）
1. 同一 sid 连续同步两次（第二次只改一个文件）。
2. 预期：正常覆盖，不因新增的包含性检查误拒（普通目录必须通过）；文件哈希正确。
3. **负向**：在保存目录里把 `<folder>.<guid8>` 预先做成指向树外的 junction（`mklink /J`）。
   预期：同步被拒，树外目录**不得**出现文件。
4. 关联改动：`ensure_contained`（canonicalize 前缀校验）。

### A11 压缩（0x08）+ 加密（0x09）
1. 传输大段可压缩文本，开启压缩与配对码（两侧同码）。
2. 预期：完成且 SHA-256 一致；无配对码/错码时被拒，且错误信息可读。
3. 关联改动：0x09 握手前 32B 证明、配对阶段 IO 错误归类为「未完成」（本轮 P1）。

### A12 配对锁定（本轮改动）
1. 故意用错配对码连续尝试 10 次（含中途断开连接的加密握手）。
2. 预期：第 10 次后该来源被锁 10 分钟；期间正确码也被拒；到期后恢复。
3. 关联改动：中断的加密握手计入失败（0x09 阶段 IO/协议错误 → AuthRejected）。

### A13 文本（0x06）与能力协商（0x0A/0x1A）
1. 双向发中文/emoji 文本；观察 0x0A 能力集交互。
2. 预期：文本完整、无乱码；未知能力被忽略而非断开。

### A14 并发分块（本轮改动）
1. C# 侧同时发起 4 个分块传输（4 个不同文件/组）。
2. 预期：全部完成、SHA-256 一致；Rust 侧单来源上限 8 组不应误伤 4 路并发。
3. 若 C# 端并发 > 8：观察是否出现「该来源的分块会话数已达上限」并使该组失败——
   记录实际并发数（这是策略边界，不是缺陷）。
4. 关联改动：0x02 单来源 8 组、全局 64 组满则拒绝。

## B. NTFS 掉电 fsync

目标：**回执成功 = 数据已落盘**。不得出现「对端报完成、重启后文件短/零尾/哈希不符」。

**方法一（推荐，唯一能真正验证掉电）**：VM（Hyper-V/VMware）跑接收端。

1. 每个用例前打快照；
2. 发起传输；
3. 在接收端出现「完成」的**同一秒**内强制断电（Hyper-V：`Stop-VM -TurnOff`；VMware：Power Off）；
4. 重启后校验文件长度与 SHA-256（与发送端源文件比）。

**方法二（无 VM 时的旁证）**：ProcMon 过滤 `Operation is FlushBuffersFile` 且
`Path contains .trft-part`（或最终名），确认 flush 出现在成功回执**之前**。
此方法证明调用顺序，不证明硬件缓存行为。

| ID | 用例 | 步骤要点 | 预期 |
|---|---|---|---|
| B1 | 0x00 单文件 1 GiB | 完成瞬间断电，重启校验 | 长度与 SHA-256 一致；不得短文件 |
| B2 | 0x01 文件夹 | 同上，校验整目录 | 全部文件完整 |
| B3 | 0x02 分块组装 | 组装完成回执瞬间断电 | 最终文件完整；`.trft-part` 残留可存在但不得冒充最终文件 |
| B4 | 0x03 续传 | 续传完成回执瞬间断电 | 最终文件完整；不得「回 status 2 但文件短」 |
| B5 | 0x04 目录同步覆盖 | 覆盖完成回执瞬间断电 | 旧文件或新文件**二者之一完整**，绝不半截 |

每条**至少 3 次**（文件系统缓存行为有随机性）；记录「文件长度 / SHA-256 / 是否回执成功」。

关联改动（本轮）：0x02 组装前 `sync_all`、v2 0x03 与 C# 方言 0x03 回执前 `sync_all`、
最终发布用原子 `rename`（0x04）。
